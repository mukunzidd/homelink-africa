Style guide for a platform whose product is trust

One colour family, used with discipline. Tea green carries the brand and the promise both; depth and form do the work that a second hue would otherwise do. Everything below serves one sentence: if it is on HomeLink, we have stood in the room.

Single-hue system Light & dark, both designed Tokens are normative

One hue, three depths

The interface has no gold. Green does the work everywhere, and the three jobs it has to hold apart are separated by depth and form rather than by a second colour — a harder discipline than a two-colour system, and a quieter result.

The rule that keeps this readable: if it is filled, it is an action. If it is ringed, it is a promise. If it is tinted with a dot, it is a status. Someone should be able to tell the three apart in greyscale — which is the test this system is actually built to pass.

Known tension, accepted deliberately. The logo is gold and the interface is not, so the mark will read as its own object rather than as part of the system. That is a legitimate choice — plenty of brands run a metallic mark over a non-metallic product — but it means the logo needs air around it and should not sit inside coloured UI chrome. Revisit if the mark ever starts to feel pasted on.

The logo, and a problem to solve

The rule: the house mark keeps its gold on any ground — it is a shape, not text, so the contrast floor does not apply. The wordmark switches to --ink on light grounds. This is a one-off asset job, not a redesign, and it is the only blocker between the logo and a shippable light theme.

Sibling groups use flex or grid gap. Per-element margins are not used for rhythm — they collapse and double in ways that are hard to trace.

Radius & elevation

  • 4px --r-chip — tags, inline code, thumbnails
  • 8px --r-ctl — buttons, inputs, transaction rows
  • 14px --r-card — discovery cards, panels, sheets

Two elevations only. --shadow-card for resting surfaces, --shadow-pop for things floating above the page. Nothing else casts a shadow.

Core components

The set every screen in the clickable shell is assembled from.

Buttons

One primary per view. Trust actions — confirming check-in, releasing escrow — use the deepest green, so the weightiest button on the page is also the calmest. A control names exactly what happens: Pay RWF 165,000, not Submit. Add-ons use secondary, never primary, because the bundle is gravity and not a gate.

The verification system

The one place HomeLink must out-design its references. A checkmark is a claim; evidence is a product. The badge is always a link, and it always opens the record below.

What the badge opens

1

Inspected in person

Jean-Claude U. visited on 12 Oct 2026. Kitchen, water pressure, power backup, and road access checked against a 34-point list.

2

Photographed by us

Every image on this listing was shot by the HomeLink team. No owner-supplied photos appear on verified listings.

3

Owner identity confirmed

Title or lease authority verified against national ID. KYC complete before any payout is possible.

4

Your money is held

Payment sits in escrow until you confirm check-in. Not as described means a full refund and another home the same night.

Rules

  • Green is never decorative. If the badge is on screen, the record exists and is reachable in one tap.
  • Never a grade. No bronze/silver/gold tiers. A listing is verified or it is not on HomeLink.
  • Name the human. A named inspector with a date, not “our team”. This is the entire difference between us and a checkbox.
  • Escrow is stated in money terms at the moment money is asked for — not buried in a trust page nobody opens.
  • The badge is ringed, never filled. That is the one form no button takes, so a promise can never be mistaken for a control — which matters most in greyscale and for colourblind users.

Phase 1 renders these records from fixtures. The fixture's shape is the shape of the verification_record table in Phase 2 — so the UI does not move when Supabase arrives.

Money and locale

Both cross-cutting, both agreed as genuinely working in Phase 1, and both expensive to retrofit across twenty screens.

RWF is a zero-decimal currency. A naive minor / 100 renders RWF 165,000 as RWF 1,650. Every amount is { minor: number, currency: ISO4217 } and every render goes through formatMoney(), which reads the currency's exponent. No component divides by 100, anywhere.

Locale rules

  • Every string via t() from day one. EN is authored; FR and RW start machine-drafted and get corrected — the wiring is what cannot be retrofitted.
  • Kinyarwanda runs long. Budget roughly 1.3× English for button and label widths. Nothing may depend on a fixed-width control.
  • Routes carry locale — /[locale]/stays/… — so listing pages are indexable per language.
  • Currency is independent of language. A diaspora user can read in Kinyarwanda and pay in USD.

Segment defaults, always overridable

  • From abroad — EN/FR, USD/EUR/GBP, card first, arrival framing, Trip prompts on.
  • From Rwanda — RW available, RWF, Mobile Money first, residential framing, listings surfaced immediately.
  • Phase 1 drives this from a visible toggle plus browser locale; Phase 2 adds the IP/geo signal.
  • The override control is persistent and visible in the header, never hidden in settings.

Motion and access

Restraint, mostly. The product is used on mid-range Android phones over patchy connections.

Motion

  • 150–200ms, ease-out for state changes — hover, selection, disclosure.
  • 240ms for sheets and drawers entering. Nothing animates longer.
  • No scroll-triggered reveals. They cost paint time and delay content on slow devices.
  • One orchestrated moment, earned: the escrow confirmation on checkout — the emotional peak of the product and the only place motion carries meaning.
  • prefers-reduced-motion honoured globally.

Access

  • 4.5:1 minimum for body text in both themes. Every brand and trust pairing is measured above, not assumed.
  • Visible focus everywhere — 2px brand ring, 2px offset. Never removed.
  • Never colour alone. Every status carries a word; every chip carries aria-pressed.
  • Touch targets 44px minimum on transaction surfaces, where mistakes cost money.
  • Both themes designed, not inverted — brand lifts to #46A87F and trust to #6FCFA5 so the depth ordering survives on a dark ground.

What this guide does not yet cover

Named honestly, so nobody assumes coverage that is not here.

  • The light-ground logo asset. Specified above, but somebody has to draw and export it. Blocker for the light theme.
  • Concierge Ops visual language. An internal tool with different density needs again — tables, bulk actions, audit trails. It inherits these tokens but needs its own layout pass.
  • Map treatment. Pin design, cluster behaviour, and the list-map split are unresolved pending a maps provider.
  • Photography direction. The verification promise says we shoot every listing; the shooting standard is a separate document and a real operational cost.
  • Email and WhatsApp templates. The channel bridge renders outside our CSS entirely and needs its own constrained token subset.
  • Illustration and empty states. Deferred until we know which empty states actually occur.
